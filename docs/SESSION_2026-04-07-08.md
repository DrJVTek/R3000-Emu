## Fixes appliqués

### 1. GetLocP/GetQ : utilise `head_lba_` au lieu de `read_lba_`
**Fichier** : `src/cdrom/cdrom.cpp` (GetLocP case 0x11, GetQ case 0x1D)

**Problème** : Pendant ReadS continu, `read_lba_` est déjà avancé au secteur suivant. Le lookup SBI pour LibCrypt ne trouvait jamais les entrées car il cherchait au mauvais LBA.

**Fix** : `const uint32_t current_lba = head_lba_;` — utilise le dernier secteur livré.

**Impact** : Nécessaire pour que LibCrypt fonctionne quand les secteurs SBI sont atteints.

### 2. GetLocP : retourne seek target pendant le seek
**Fichier** : `src/cdrom/cdrom.cpp` (GetLocP)

**Problème** : Quand le jeu appelle GetLocP avant que le premier secteur arrive (pendant le seek), `head_lba_` contient encore l'ancienne position. Le jeu reçoit une position inattendue.

**Fix** :
```cpp
const uint32_t current_lba =
    (reading_active_ && (seek_in_progress_ || seek_pending_ || read_pending_irq1_))
        ? read_lba_    // target position during seek
        : head_lba_;   // last delivered sector
```

### 3. Queued command dispatch : retiré `pending_irq_type_ == 0`
**Fichier** : `src/cdrom/cdrom.cpp` (ACK handler, queued command dispatch)

**Problème** : Un GetLocP queué ne pouvait jamais s'exécuter pendant ReadS continu car `pending_irq_type_` (secteur en attente) bloquait la condition. DuckStation n'a pas cette restriction — les commandes s'exécutent indépendamment des secteurs pendants.

**Fix** : Retiré `pending_irq_type_ == 0` de la condition de dispatch au line ~3431.

**Impact** : GetLocP peut maintenant s'exécuter même quand un secteur est en queue de livraison.

### 4. Timer 2 sysclk/8 : pas skippé dans le thread
**Fichier** : `src/r3000/bus.cpp` (timer_thread_func)

**Problème** : Le timer thread skippait TOUS les timers avec `use_external_clock`. Pour Timer 2, external clock = sysclk/8 qui est dérivé du CPU — pas une source externe comme HBlank. Résultat : Timer 2 en mode sysclk/8 n'était tick'é par personne (thread skip + main loop skip).

**Fix** : `if (t.use_external_clock && ch != 2)` — Timer 2 reste dans le thread.

### 5. Timer 2 reset_at_target dans le thread
**Fichier** : `src/r3000/bus.cpp` (timer_thread_func)

**Problème** : Quand Timer 2 atteignait sa target (ex: 0x1000), le thread calculait `ticks_to_event = 0xFFFF` car `count >= target`. Le sleep devenait ~15ms > cap 2ms, et la condition `sleep_ns <= max_sleep` empêchait le fire. Le timer se bloquait définitivement à count=target.

**Fix** : Reset count à 0 quand `reset_at_target && count >= target` avant le calcul.

**Impact** : **Débloque Crash Bandicoot** — le jeu passe maintenant les logos et arrive au gameplay. Le tick counter (DAT_80034520) avance correctement.

### 6. Timer thread : spin-wait hybride
**Fichier** : `src/r3000/bus.cpp` (timer_thread_func)

**Problème** : `std::this_thread::sleep_for` a une précision de ~15ms sur Windows. Les timers PS1 fire souvent à ~1ms (Timer 2 target=0x1000 à sysclk/8 ≈ 0.97ms).

**Fix** : Sleep en chunks de 500µs, puis spin-wait avec `yield()` les dernières 200µs.

**Impact** : Précision timer ~1-10µs au lieu de ~15ms. Plus de cap 2ms qui bloquait les timers longs.

Puis en continuant après ce point :

Donc :

Validation complémentaire :

### Mise à jour 2026-04-08 (nuit) — `state 9` atteint naturellement

Nouveau point important :
- après la réparation du vieux stall LibCrypt, Soul Reaver ne s'arrête pas en `state 8`
- un watchpoint RAM sur `st` montre la séquence :
  - `4 -> 8 -> 9`

Captures runtime :
- `st = 8` à `pc = 0x80039060`
- `st = 9` à `pc = 0x80039060`
- à l'entrée en `state 9` :
  - `vi = 0xFFFFFFFF`
  - `ceec0 = 1`
  - `cd2e0 = 0x80036C84`
  - `cd2e4 = 0x80036DC0`

Les lectures CD continuent pendant cette phase :
- `ReadN` sur `BIGFILE.DAT`
- `DMA3` actif
- `LBA` qui avancent

Décompilation Ghidra :
- `FUN_80038F34()` :
  - `case 8` installe la transition puis pose `state = 9`
  - `case 9` appelle `FUN_80038e60(...)`
- `FUN_80038e60()` ressemble à un tick principal de runtime, pas à une boucle d'erreur

Conclusion pratique :
- il n'y a pas de nouveau stall immédiat après LibCrypt
- le jeu atteint bien sa boucle principale `state 9`
- les writes répétées de `st = 9` vues par les watchpoints sont normales : le dispatcher réécrit l'état courant à chaque frame

### Localisation exacte
Le jeu se bloque dans `FUN_80038f34` (state machine), case 4 :
```c
do {
    DAT_800ceec0 = (DAT_800cd2e0 == 0 && DAT_800cd2e4 == 0);
} while (DAT_800ceec0 == 0);
FUN_80074530("GOT KEY");  // ← jamais atteint
```

### Ce qui ne fonctionne pas
Le build courant montre un problème plus fin que "plus aucun IRQ CD".

- `GetLocP` continue de retourner des positions qui avancent,
- le callback final côté jeu est bien exécuté autour de `0x800C12D4/0x800C12F8`,
- mais la chaîne ne converge jamais vers la sortie :
  - `cd2e0 -> 0`
  - `cd2e4` reste non-null
  - `ceec0` reste `0`

### Hypothèse principale
Le bug restant n'est probablement plus dans la lecture brute des secteurs,
mais dans la sémantique de la chaîne LibCrypt finale :
1. ordre/status des callbacks CD non conforme
2. valeur de `cd5bc` ou résultat de callback jamais vue comme "bonne"
3. différence de contrat runtime entre notre émulation et DuckStation sur cette phase

### Nouveau résultat décisif (MCP runtime)

Le stall a été cassé expérimentalement **sans modifier le jeu** via un step hook MCP :

- hook unique à `pc=0x80039240`
- action : écrire `0` dans `DAT_800cd2e4` (`phys 0x000CD2E4`)

Effet observé :
- le hook tire une fois,
- Soul Reaver sort de `state=4`,
- passe en `state=9`,
- `vidx` devient `-1`,
- les callbacks reviennent sur les pointeurs libcd standards.

Conclusion :
- `cd2e0` n'est pas le verrou final,
- le verrou final est que `cd2e4` reste non-null,
- le bug réel à corriger dans l'émulateur est ce qui empêche le callback final LibCrypt de remettre `cd2e4` à `0`.

### Confirmation DuckStation (GDB)

Comparaison directe faite avec DuckStation via le GDB server :

- breakpoint à `0x80039240` :
  - DuckStation est bien en `st=4`, `vi=5`
  - **mais** `cd2e4 = 0`
- breakpoint à `0x800C12F8` :
  - DuckStation passe bien par ce callback intermédiaire
  - `cd2e4 = 0x800C12F8` à ce moment-là
- watchpoints sur `0x800CD2E4` :
  - DuckStation enchaîne plusieurs pointeurs de callback
  - observés : `0x800C12D4`, `0x800C12F8`, `0x800C131C`

Conclusion pratique :
- DuckStation exécute une petite machine de réarmement des callbacks LibCrypt,
- puis finit par arriver à la boucle principale avec `cd2e4 = 0`,
- alors que chez nous la chaîne finit bloquée avec `cd2e4 = 0x800C12F8`.

### Confirmation côté R3000-Emu

Des step hooks MCP ont été posés sur `0x800C131C` et `0x800C1424`
une fois le stall atteint (`st=4`, `vi=5`, `cd2e4=0x800C12F8`).

Résultat :
- aucun hit sur `0x800C131C`
- aucun hit sur `0x800C1424`

Donc notre chaîne ne passe jamais par les étapes suivantes que DuckStation
exécute encore. Le vrai verrou est donc la transition manquante
**après `0x800C12F8` et avant `0x800C131C`**.

### Nouveau lead générique (2026-04-08 soir)

La comparaison DuckStation a révélé quelque chose de beaucoup plus générique qu'un hack Soul Reaver :

- DuckStation livre `INT1/DataReady` via une vraie file async :
  - `SetAsyncInterrupt(Interrupt::DataReady)`
  - puis `DeliverAsyncInterrupt()`
  - puis `interrupt_flag_register = DataReady`
- ce chemin est indépendant de `BFRD`
- `BFRD` ne contrôle que la disponibilité FIFO/DMA (`DRQSTS`), pas l'existence de l'événement secteur-ready

Dans notre core, le chemin continu `ReadS/ReadN` avait une divergence probable :

- après `try_fill_data_fifo()`
- si rien n'était poussé dans la FIFO
- on reschedulait le secteur suivant et on `return`
- donc on sautait complètement `set_async_irq(INT1)`

Or juste après le réarmement LibCrypt `cd2e4 = 0x800C12F8`, les traces montrent précisément :

- `want_data_ = 0`
- les secteurs continuent d'avancer
- mais plus aucun `INT1` n'atteint le callback guest

Hypothèse forte :

- on supprime l'`INT1` secteur-ready uniquement parce que `want_data_ == 0`
- alors que sur vrai hardware et dans DuckStation, `want_data_` ne doit bloquer que le FIFO/DMA, pas l'IRQ `DataReady`

Patch candidat actuellement posé :

- ne plus court-circuiter la livraison `INT1` lorsque `try_fill_data_fifo()` n'écrit rien **si** `want_data_ == 0`
- autrement dit : `want_data_ == 0` doit empêcher la donnée FIFO, pas l'événement secteur-ready

Validation runtime finale encore à refaire proprement, mais c'est aujourd'hui le meilleur bug générique identifié.
